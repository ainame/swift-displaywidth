# Bump the supported Unicode version

1. Check the [Unicode releases page](https://www.unicode.org/releases/) for the latest final Unicode Standard version. **Read that version's official notes, including its change summary and migration guidance, before inspecting or changing repository code.** Identify changes relevant to display width and this package's data sources. If the version page still shows draft boilerplate, use the release index to confirm final status. Confirm that the versioned `ucd/UnicodeData.txt` and `ucd/EastAsianWidth.txt` files exist under `https://www.unicode.org/Public/<version>/`; do not substitute beta data.
2. Inspect the current branch, working tree, `Sources/Generate/Command.swift`, `Sources/DisplayWidth/DisplayWidth.swift`, `Tests/DisplayWidthTests/`, `README.md`, `CHANGELOG.md`, and version references before editing. Start from current `origin/main` when creating a new branch. If the supported version is already current, report that result without regenerating or opening a PR.
3. Update the generator's version, run `swift run generate`, and commit `Sources/DisplayWidth/UnicodeData.generated.swift`. Keep the generator responsible for generated output. Check whether the new Unicode files introduce property values, range formats, or newly assigned characters that require parser or width-logic changes. In particular, `UnicodeData.txt` uses paired `<..., First>` and `<..., Last>` rows for whole ranges; verify that interior code points are represented.
4. Add focused regression tests for changed behavior: a newly assigned combining mark, wide character or emoji, and any changed range handling when relevant. Use scalar tests when the installed Swift runtime may segment a new character differently. Update the README data links, the Unreleased changelog entry, and any other repository version references. Distinguish the generated General Category and East Asian Width tables from `Character` grapheme segmentation supplied by the Swift runtime.
5. Run `swift test`, `git diff --check`, and a second generation pass to check that the generated file is identical. Honor `.swift-version`; on macOS, a Swiftly toolchain may need a compatible `DEVELOPER_DIR` and a fresh SwiftPM scratch path if the selected Xcode SDK causes compiler argument errors. Record the exact toolchain, commands, and results. Do not treat a different toolchain's passing tests as validation of the requested Swiftly version.
6. Prepare a short previous-version-to-new-version summary for the PR from the official notes read at the start. Link the version page and release index, and distinguish Unicode-wide changes from behavior this package actually implements.
7. Commit meaningful changes and, when a PR is requested, push and create or update the PR using a body file. Include the official diff summary and links, before/after behavior, tests, generated-file status, and any runtime segmentation limitation. Verify draft state and hosted checks when the request calls for a draft PR.
